# Аналіз кодової бази проєкту Voxeterra

Проєкт **Voxeterra** — це воксельний рушій, написаний на C++ з використанням графічного API Vulkan. Код дуже добре структурований, використовує сучасні можливості C++ (smart pointers, RAII) та має чіткий розподіл на підсистеми: ядро (Engine), управління станами, генерація та рендеринг світу, графічний інтерфейс (UI) та обгортки над Vulkan.

Нижче наведено детальний аналіз кожного файлу, його призначення, а також сильні (плюси) та слабкі (мінуси) сторони.

---

## 1. Ядро (Core)

### `main.cpp`
**Опис:** Точка входу в програму. Ініціалізує рушій та запускає головний цикл. Містить кросплатформенний код для визначення директорії виконуваного файлу.
- **Плюси:** Дуже чистий `main()`. Розумне рішення змінити робочу директорію (`current_path`) на директорію .exe файлу, що дозволяє легко завантажувати ресурси (шейдери, шрифти) незалежно від того, звідки запущена гра.
- **Мінуси:** Платформозалежний код (Win32, macOS, Linux) краще було б винести в окремий файл (наприклад, `utils/Platform.hpp`), щоб не засмічувати точку входу.

### `src/Engine.cpp` та `headers/Engine.hpp`
**Опис:** Головний клас рушія. Зв'язує всі системи разом (Window, Vulkan, Input, StateManager, WorldRenderer, UIRenderer). Керує головним ігровим циклом та синхронізацією кадрів.
- **Плюси:** Правильний порядок знищення об'єктів (в зворотному порядку до їх створення завдяки RAII). Чіткий поділ на ініціалізацію, оновлення (update) та малювання (draw). 
- **Мінуси:** Це "Божественний об'єкт" (God Object), який робить забагато речей. Зокрема, низькорівнева логіка Vulkan (наприклад, `vkQueuePresentKHR`, `vkAcquireNextImageKHR` та налаштування `VkSubmitInfo`) знаходиться тут. Її варто було б винести в окремий клас `Renderer` або `VulkanContext`.

### `src/Window.cpp` та `headers/Window.hpp`
**Опис:** Обгортка над GLFW для створення вікна.
- **Плюси:** Використовує `std::unique_ptr` з кастомним `deleter` для безпечного управління пам'яттю `GLFWwindow`. Правильно обробляє зміну розміру вікна.
- **Мінуси:** Витік абстракції — метод `getWindow()` повертає сирий вказівник `GLFWwindow*`, що змушує інші класи (наприклад, `InputManager`) залежати від GLFW.

### `src/Config.cpp` та `headers/Config.hpp`
**Опис:** Завантаження та збереження налаштувань гри з файлу `config.json` за допомогою бібліотеки `nlohmann/json`.
- **Плюси:** Простий, зрозумілий інтерфейс. Наявність значень за замовчуванням на випадок відсутності конфігу.
- **Мінуси:** При помилці парсингу або читання просто виводиться повідомлення в консоль. Можна додати більш надійну обробку помилок або повідомлення користувачеві в UI.

### `src/Camera.cpp` та `headers/Camera.hpp`
**Опис:** Стандартна FPS (First Person Shooter) камера. Обчислює View та Projection матриці.
- **Плюси:** Коректно обробляє рух миші, використовує кватерніони (через вектори) та має захист від "gimbal lock" (обмеження pitch до 89 градусів).
- **Мінуси:** Швидкість камери "зашита" прямо в коді (`velocity = 40.0f * deltaTime;`). Її варто було б брати з `Config` або передавати як параметр.

## 2. Керування станами (State Management)

### `src/StateManager.cpp` та `headers/StateManager.hpp`
**Опис:** Реалізує патерн State. Керує переходами між станами гри (Меню, Гра, Пауза).
- **Плюси:** Перехід між станами відкладений (відбувається на початку наступного кадру завдяки `m_shouldChangeState`), що запобігає багам із видаленням поточного стану під час його ж оновлення.
- **Мінуси:** Немає стеку станів (State Stack). Наприклад, коли ми виходимо з меню паузи, ми просто перемикаємось на `PLAYING`, замість того щоб "зняти" стан паузи зі стеку.

### `headers/GameState.hpp`
**Опис:** Інтерфейс (абстрактний клас) `IGameState`, який повинні реалізувати всі стани.
- **Плюси:** Має всі необхідні методи життєвого циклу (`onEnter`, `onExit`, `update`, `render`, `handleInput`).
- **Мінуси:** Методи `shouldRenderWorld` та `getUIRoot` трохи порушують принцип єдиної відповідальності, прив'язуючи логіку стану безпосередньо до механіки рендерингу конкретного рушія.

### `States/MainMenuState.cpp`, `PlayingState.cpp`, `PausedState.cpp`
**Опис:** Конкретні стани гри. `PlayingState` також включає логіку "F3 Debug меню" (показ FPS, позиції, кількості чанків).
- **Плюси:** Дуже чиста ізоляція логіки. Кожен стан самостійно створює свій UI і не заважає іншим. В `PlayingState` чудово реалізовано лічильник FPS.
- **Мінуси:** Всі UI-елементи мають жорстко закодовані розміри та позиції (магічні числа на кшталт `0.35f, 0.18f`). Якщо зміниться співвідношення сторін екрану, UI може виглядати розтягнутим.

## 3. Світ та Вокселі (World)

### `headers/World/Voxel.hpp`
**Опис:** Визначає тип вокселя.
- **Плюси:** Використання `uint8_t` (1 байт) для вокселя робить чанки надзвичайно легкими в пам'яті (всього 256 КБ на чанк 64x64x64). Зручні inline функції (`isVoxelOpaque`, `isVoxelTransparent`).
- **Мінуси:** Функція `voxelTypeToColor` жорстко кодує кольори вокселів. Для серйозної гри знадобиться текстурний атлас замість суцільних кольорів.

### `src/World/Chunk.cpp` та `headers/World/Chunk.hpp`
**Опис:** Зберігає дані 64x64x64 блоків та генерує сітку (mesh) чанка.
- **Плюси:** **Надзвичайно оптимізований алгоритм Binary Greedy Meshing!** Використання 64-бітних масок (`uint64_t`) та вбудованих функцій пошуку нулів (`ctz64`) для генерації об'єднаних полігонів — це топове рішення для продуктивності. Розділення на звичайний і водяний (прозорий) меш.
- **Мінуси:** Алгоритм мешингу жорстко зав'язаний на розмір чанка рівно `64` (через використання 64-бітного числа). Змінити розмір чанка на 32 чи 128 без переписування алгоритму неможливо.

### `src/World/World.cpp` та `headers/World/World.hpp`
**Опис:** Зберігає всі чанки в `unordered_map`, виконує процедурну генерацію ландшафту (за допомогою Fractional Brownian Motion).
- **Плюси:** Швидкий доступ до чанків за допомогою кастомного хешу (`IVec3Hash`). Генерація рельєфу (value noise, fbm2D) працює чудово і генерує гори, пагорби та океани.
- **Мінуси:** Генерація чанків і створення мешів відбувається **на головному потоці** (`generateChunkData`, `generateMesh`). Це призведе до зависання (stuttering) гри під час переміщення гравця. Необхідно винести це в `std::thread` або Thread Pool.

### `src/World/WorldRenderer.cpp` та `headers/World/WorldRenderer.hpp`
**Опис:** Керує рендерингом світу, стрімінгом чанків та містить пайплайни (звичайний та для води).
- **Плюси:** Хороша система стрімінгу (`updateStreaming`) — чанки завантажуються ближчі до камери в першу чергу. Наявність Frustum Culling (`aabbInFrustum`) — невидимі чанки взагалі не відправляються на GPU, що сильно економить ресурси.
- **Мінуси:** Під час створення буферів для нових чанків щоразу викликається `vkAllocateMemory`. Vulkan має жорстке обмеження на кількість одночасних алокацій пам'яті (зазвичай 4096). Це швидко призведе до крашу при великому Render Distance. Потрібно використовувати кастомний алокатор (наприклад, Vulkan Memory Allocator - VMA).

## 4. Ввід (Input)

### `src/Input/InputManager.cpp` та `headers/Input/InputManager.hpp`
**Опис:** Обробка миші та клавіатури.
- **Плюси:** Відстежує не лише факт натискання, але й "фронти" (`isKeyPressed`, `isKeyReleased`), зберігаючи стан з попереднього кадру. Зручні методи для нормалізованої позиції миші (використовується в UI).
- **Мінуси:** Клавіші реєструються для перевірки "ліниво" (при першому запиті). Це може призвести до пропуску першого натискання, якщо `isKeyPressed` викликано вперше саме в момент натискання.

## 5. Графічний інтерфейс (UI)

### `UIElement`, `UIPanel`, `UIButton`, `UILabel`
**Опис:** Ієрархічна система віджетів для створення інтерфейсів.
- **Плюси:** Класичний та зрозумілий об'єктно-орієнтований підхід. `UIButton` чудово обробляє стани (hover, pressed) та має колбеки (`std::function`). Ієрархія дозволяє групувати елементи в `UIPanel`.
- **Мінуси:** Немає системи компонування (Layout System). Доводиться вручну вказувати координати.

### `src/UI/UIRenderer.cpp` та `headers/UI/UIRenderer.hpp`
**Опис:** Рендерить дерево UI в один буфер та малює за один Draw Call.
- **Плюси:** Дуже швидкий підхід — весь UI батчиться в єдиний масив вершин. Є підтримка Truetype шрифтів (завдяки `stb_truetype`) і навіть вбудований fallback у вигляді растрового піксельного шрифту на випадок відсутності `.ttf` файлу!
- **Мінуси:** `m_vertexBuffer` перезаписується на кожному кадрі. Якщо UI великий, часті оновлення буфера можуть бути неефективними. Краще використовувати кільцевий буфер (Ring Buffer) або декілька буферів для кожного кадру (In-flight frames).

## 6. Обгортки Vulkan (Vulkan API Wrappers)

Весь код у папці `src/Vulkan/` розроблений для спрощення роботи з багатослівним API Vulkan.

- **`Instance.cpp` / `Device.cpp` / `Swapchain.cpp`**: 
  - *Плюси:* Коректна ініціалізація. Враховані нюанси macOS (`VK_KHR_portability_subset`). Добре розділена логіка вибору фізичного та логічного пристроїв.
  - *Мінуси:* Жорстко задані вимоги (тільки графіка і презентація). Немає підтримки Compute черг для майбутнього розвитку.
- **`Framebuffer.cpp` / `RenderPass.cpp` / `DepthBuffer.cpp`**: 
  - *Плюси:* Надійна інкапсуляція. Створюють коректні залежності (`VkSubpassDependency`) для синхронізації запису кольору і глибини.
- **`Pipeline.cpp` / `Pipeline2D.cpp`**: 
  - *Плюси:* Розділені пайплайни для 3D та 2D. `Pipeline2D` використовує динамічний viewport/scissor, що дозволяє змінювати розмір вікна без перестворення пайплайну. Підтримка Alpha Blending для води та UI.
  - *Мінуси:* `Pipeline.cpp` має надто багато "захардкоджених" налаштувань (шляхи до шейдерів, формати вершин). Було б краще зробити його більш універсальним через структуру-білдер (PipelineBuilder).
- **`CommandPool.cpp` / `Buffer.cpp` / `Shader.cpp`**: 
  - *Плюси:* Класичні RAII обгортки. При знищенні об'єкта ресурси автоматично звільняються (`vkDestroy...`).
  - *Мінуси:* `Buffer::copyData` використовує синхронний `vkMapMemory` / `vkUnmapMemory`. Для частих оновлень краще тримати пам'ять постійно замапленою (Persistent Mapping).
- **`TextRenderer.cpp`**: 
  - *Плюси:* Чудове використання `stb_truetype` для створення атласу шрифтів на льоту. Динамічне вимірювання ширини тексту.
  - *Мінуси:* Завантажує лише символи ASCII (32-126). Немає підтримки кирилиці чи інших Unicode символів. Не використовує Staging Buffer для завантаження текстури шрифту в VRAM, що зменшує швидкість рендерингу тексту на деяких GPU.

## Загальний висновок
**Проєкт написаний на дуже високому рівні.** Архітектура продумана, управління пам'яттю безпечне, а алгоритм генерації сітки вокселів заслуговує на окрему похвалу за креативність (бінарний greedy meshing).

**Головні напрямки для покращення (щоб зробити з цього комерційний рушій):**
1. **Багатопоточність (Multithreading):** Винести генерацію чанків у фонові потоки.
2. **Управління пам'яттю GPU:** Впровадити VMA (Vulkan Memory Allocator), щоб уникнути ліміту алокацій Vulkan.
3. **Атлас текстур:** Замість суцільних кольорів використовувати текстури для блоків (земля, камінь).
4. **Юнікод:** Розширити `TextRenderer` для підтримки кирилиці та UTF-8.
