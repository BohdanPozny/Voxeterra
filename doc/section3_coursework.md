# РОЗДІЛ 3. КЕРІВНИЦТВО КОРИСТУВАЧА

У цьому розділі представлено покрокове керівництво з підготовки робочого середовища, збирання та використання воксельного рушія *Voxterra*. Описано системні та програмні вимоги, послідовність встановлення залежностей, процес компіляції з вихідного коду, запуск програми, опис усіх режимів роботи (головне меню, ігровий режим, меню паузи), формат файлу конфігурації *config.json*, опис елементів керування, типові повідомлення для користувача та можливі помилки. Метою розділу є надання користувачу повного розуміння того, як розгорнути та використовувати програмний продукт на власній машині.

## 3.1 Системні та програмні вимоги

Воксельний рушій *Voxterra* є нативним *C++*-застосунком, який використовує графічний *API Vulkan* для безпосередньої взаємодії з графічним процесором. Тому до апаратного та програмного забезпечення висуваються наступні вимоги.

**Апаратні вимоги (мінімальні):**

- Центральний процесор з підтримкою інструкцій *x86-64* (Intel Core i3 / AMD Ryzen 3 чи новіше);
- Не менше 4 ГБ оперативної пам'яті;
- Графічний процесор із підтримкою *Vulkan 1.2* або новіше: *NVIDIA* серії *GeForce GTX 600+* (драйвер 418+), *AMD Radeon HD 7000+* (драйвер 18.1+) або інтегрована графіка *Intel HD Graphics 500-ї* серії та новіше з актуальним драйвером;
- Близько 200 МБ вільного місця на диску для вихідного коду, скомпільованих об'єктних файлів та виконуваного файлу.

**Апаратні вимоги (рекомендовані):**

- 16 ГБ оперативної пам'яті при значеннях параметра *renderDistance* більше 32 чанків;
- Дискретний графічний процесор (наприклад, *NVIDIA GeForce GTX 1060* або *AMD Radeon RX 580* і вище) для забезпечення стабільних 60 кадрів на секунду при роздільній здатності *1920×1080*;
- *SSD*-носій для прискорення компіляції шейдерів та запуску програми.

**Програмні вимоги:**

- Операційна система: *Linux* (будь-який сучасний дистрибутив – *Ubuntu* 22.04+, *Fedora* 38+, *Arch Linux*, *NixOS*), *Windows 10/11* (64 біт) або *macOS* 12.0+ із встановленим *MoltenVK*;
- Компілятор з підтримкою стандарту *C++20*: *GCC* 11+, *Clang* 13+ або *MSVC* з *Visual Studio 2022* (версія компілятора 19.30+);
- Система автоматизації збирання *CMake* версії 3.16 або новіше;
- *Vulkan SDK* версії 1.2.176+ (включає компілятор шейдерів *glslc*);
- Бібліотеки розробника *GLFW 3* (керування вікном і введенням) та *GLM* (математичні типи для шейдерної алгебри);
- Шрифт *TrueType* (*.ttf*) для відображення тексту інтерфейсу (постачається разом з проєктом у теці `fonts/`).

Якщо одна з вимог не виконана (зокрема, відсутній *Vulkan*-сумісний драйвер графічного процесора), запуск програми неможливий і вона завершиться з повідомленням про помилку ініціалізації *Vulkan*-екземпляра.

## 3.2 Встановлення залежностей

Для розгортання середовища збирання необхідно встановити необхідні бібліотеки розробника. Команди наводяться для трьох основних операційних систем.

**Ubuntu / Debian:**

```bash
sudo apt update
sudo apt install build-essential cmake git \
    vulkan-tools libvulkan-dev vulkan-validationlayers-dev \
    libglfw3-dev libglm-dev glslang-tools
```

**Fedora / RHEL:**

```bash
sudo dnf install gcc gcc-c++ cmake git \
    vulkan-devel vulkan-tools \
    glfw-devel glm-devel glslc
```

**Arch Linux:**

```bash
sudo pacman -S base-devel cmake git \
    vulkan-devel vulkan-tools \
    glfw glm shaderc
```

**NixOS:** проєкт містить готовий файл `shell.nix`, тож достатньо виконати команду `nix-shell` у кореневій теці – середовище буде підготовлене автоматично з усіма необхідними бібліотеками.

**Windows:** встановити *Visual Studio 2022 Community* з робочим навантаженням «Desktop development with C++», після чого завантажити та встановити *Vulkan SDK* з офіційного сайту *LunarG* (`https://vulkan.lunarg.com`). Бібліотеки *GLFW* та *GLM* можна отримати через пакетний менеджер *vcpkg*:

```powershell
vcpkg install glfw3:x64-windows glm:x64-windows
```

Після встановлення *Vulkan SDK* змінна середовища `VULKAN_SDK` встановлюється автоматично. Це дозволяє *CMake* знайти компілятор шейдерів `glslc.exe`.

## 3.3 Отримання та збирання проєкту

Вихідний код проєкту знаходиться у системі контролю версій *Git*. Послідовність дій для отримання та збирання застосунку.

**Крок 1.** Клонувати репозиторій проєкту.

```bash
git clone https://github.com/BohdanPozny/Voxeterra.git
cd Voxeterra
```

**Крок 2.** Згенерувати файли збирання за допомогою *CMake*.

Для *Linux* та *macOS*:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
```

Для *Windows*:

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
```

На цьому етапі *CMake* перевіряє наявність усіх залежностей, налаштовує параметри компіляції *C++20* та формує правила збирання.

**Крок 3.** Скомпілювати проєкт.

```bash
cmake --build build -j
```

Прапорець `-j` вказує системі використовувати всі доступні ядра процесора для прискорення компіляції. Під час збирання *CMake* автоматично викликає `glslc` для трансляції *GLSL*-шейдерів у бінарний формат *SPIR-V*, який буде завантажений рушієм у момент створення графічних конвеєрів. Файли *fonts/default.ttf* та *config.json* копіюються у каталог зі скомпільованим виконуваним файлом, щоб програма могла знайти їх відносно власного шляху під час запуску.

## 3.4 Запуск програми

Запуск виконується з командного рядка з кореневого каталогу проєкту:

**Linux / macOS:**

```bash
./build/Voxterra
```

```powershell
./build/Release/Voxterra.exe
```

## 3.5 Портативність та структура виконуваного каталогу

Завдяки відокремленню логіки визначення шляхів в окремий модуль `Platform`, рушій *Voxterra* є повністю портативним (portable). Це означає, що програма не потребує складного процесу інсталяції у систему (наприклад, через інсталятори або реєстр Windows) і може запускатися безпосередньо з будь-якого носія, включаючи змінні (USB-накопичувачі).

Для перенесення розгорнутої програми на інший комп'ютер достатньо скопіювати згенерований виконуваний файл (`Voxterra` або `Voxterra.exe`) та розмістити поруч із ним необхідні ресурси:
- теку `shaders/` (із скомпільованими `.spv` файлами шейдерів);
- теку `fonts/` (з файлом шрифту `default.ttf`);
- файл конфігурації `config.json`.

Модуль `Platform` динамічно визначає абсолютний шлях до виконуваного файлу в момент запуску і встановлює його як поточну робочу директорію (`std::filesystem::current_path`). Завдяки цьому програму можна запускати з командного рядка з будь-якої іншої теки, не порушуючи відносні шляхи до ресурсів.

## 3.6 Робота з програмою

Програма працює у графічному режимі і має три основні стани, між якими користувач переходить за допомогою клавіатури або миші. Перехід між станами реалізовано через скінченний автомат `StateManager`, який описано в розділі 2.

### Головне меню

Після запуску програма перебуває у стані `MAIN_MENU`. На екрані відображаються дві кнопки, розміщені по центру вікна:

- **New Game** (зелена) – переводить програму у стан `PLAYING` і починає рендеринг воксельного світу. Курсор миші захоплюється вікном для керування камерою у стилі *FPS*-ігор;
- **Exit** (червона) – викликає `glfwSetWindowShouldClose`, що змушує головний цикл коректно завершитись після поточного кадру; вікно закривається, всі *Vulkan*-ресурси звільняються через ланцюжок деструкторів.

Кнопки реагують на наведення курсора: початковий колір змінюється на світліший відтінок (стан *hover*), при натисканні – на темніший (стан *pressed*). Клік фіксується по фронту натискання (edge-trigger), тому утримання кнопки миші не призводить до повторних спрацьовувань.

### Ігровий режим

При натисканні кнопки **New Game** активується стан `PLAYING`. На екрані відображається тривимірний воксельний світ із процедурно згенерованим рельєфом, що складається з шарів каменю, ґрунту та трави. Камера встановлюється у фіксовану позицію над поверхнею (висота 60 блоків, координата *X* = 16, *Z* = 16). Курсор приховується (режим *GLFW_CURSOR_DISABLED*) – переміщення миші використовується для повороту камери.

- **Esc** – вихід у меню паузи.

У лівому верхньому куті завжди відображається *HUD*-панель з лічильником кадрів на секунду (*FPS*), який оновлюється двічі на секунду. Це допомагає швидко оцінити продуктивність при зміні параметрів конфігурації.

При натисканні клавіші **F3** активується дебаг-оверлей, що додає п'ять текстових міток з технічною інформацією: координати камери в світі (*XYZ*), напрямок погляду камери (*Dir*), номер поточного чанка та кут огляду (*FOV*), кількість вершин і трикутників у завантажених мешах (*Verts/Tris*), кількість видимих та завантажених чанків (*Chunks*). Повторне натискання F3 приховує оверлей.

Під час руху камери модуль стрімінгу `WorldRenderer::updateStreaming` динамічно завантажує нові чанки, які потрапляють у радіус видимості, та вивантажує ті, що покинули радіус (з гістерезисом в один чанк, щоб уникнути «миготіння» на межі). ### Меню паузи

Натискання клавіші **Esc** в ігровому режимі переводить програму у стан `PAUSED`. Особливістю реалізації є те, що метод `PausedState::shouldRenderWorld()` повертає `true`, тому тривимірний світ продовжує рендеритись, але оновлення стрімінгу зупиняється – світ візуально «застигає». Поверх нього малюється напівпрозорий чорний оверлей (55% непрозорості) з трьома елементами:

- Заголовок **PAUSED** великим шрифтом по центру екрана;
- Кнопка **Resume** (зелена) – повертає у стан `PLAYING`;
- Кнопка **Main Menu** (червона) – повертає у стан `MAIN_MENU`, фактично завершуючи поточну ігрову сесію.

## 3.7 Конфігурація

Поведінка програми налаштовується через файл `config.json`, який знаходиться у теці з виконуваним файлом. Файл зчитується при запуску методом `Config::load`. Якщо файл відсутній або містить синтаксичні помилки, рушій використовує значення за замовчуванням і виводить попередження у консоль. Структура файлу.

```json
{
  "audio": {
    "masterVolume": 1.0,
    "musicVolume": 0.7,
    "sfxVolume": 0.8
  },
  "controls": {
    "mouseSensitivity": 0.1,
    "movementSpeed": 10.0
  },
  "graphics": {
    "fov": 70.0,
    "fullscreen": false,
    "renderDistance": 32,
    "vsync": true,
    "windowHeight": 1080,
    "windowWidth": 1920
  },
  "ui": {
    "font": "fonts/default.ttf",
    "fontSize": 16
  }
}
```

**Опис ключових параметрів:**

- `graphics.windowWidth` та `graphics.windowHeight` – розміри вікна у пікселях;
- `graphics.fullscreen` – якщо `true`, вікно відкривається у повноекранному безрамковому режимі з нативною роздільністю монітора;
- `graphics.renderDistance` – радіус видимості у чанках. Значення 32 означає квадрат 64×64 чанки, тобто 4096 чанків у площині *XZ*. Цей параметр найбільше впливає на продуктивність: збільшення радіуса вдвічі чотирикратно збільшує кількість завантажуваних чанків;
- `graphics.fov` – кут поля зору (*field of view*) у градусах; типове значення 70°, допустимий діапазон 1°-90°;
- `graphics.vsync` – вертикальна синхронізація з частотою оновлення монітора;
- `controls.mouseSensitivity` – множник для дельти миші;
- `controls.movementSpeed` – швидкість переміщення камери (наразі використовується константа в коді, параметр зарезервований для розширень).

Для зміни параметрів достатньо відредагувати файл у будь-якому текстовому редакторі та перезапустити програму. Видалення файлу `config.json` змусить рушій відновити його з типовими значеннями.

## 3.8 Рекомендації щодо оптимізації продуктивності

Воксельний рушій є ресурсомісткою програмою через необхідність динамічно генерувати великі обсяги геометрії. Якщо під час гри виникають затримки або значення *FPS* у *HUD*-панелі падає нижче комфортного рівня (наприклад, нижче 60), користувачеві рекомендується вжити наступних заходів:

1. **Зменшення радіуса видимості.** Найбільший вплив на продуктивність має параметр `graphics.renderDistance` у файлі `config.json`. Його зменшення з 32 до 16 або 8 експоненціально зменшить навантаження на процесор та оперативну пам'ять, оскільки кількість чанків розраховується як площа кола.
2. **Аналіз F3-оверлею.** Увімкнення дебаг-оверлею (клавіша F3) дозволяє проаналізувати кількість завантажених вершин (`Verts`) та трикутників (`Tris`). Якщо ці значення перевищують кілька мільйонів, графічний адаптер може не встигати їх обробляти. 
3. **Вимкнення V-Sync.** На слабких системах параметр `graphics.vsync = false` може допомогти уникнути штучного обмеження кадрів, коли відеокарта трохи не встигає за частотою оновлення монітора.
4. **Використання Release збірки.** Переконайтеся, що програма скомпільована з прапорцем `CMAKE_BUILD_TYPE=Release`, оскільки оптимізації компілятора прискорюють алгоритм *Greedy Meshing* більше ніж у 10 разів порівняно з конфігурацією *Debug*.

## 3.9 Повідомлення для користувача та обробка помилок

Програма передбачає декілька типів повідомлень, які виводяться в консольний потік виведення. Залежно від рівня важливості повідомлення спрямовуються або в `std::cout` (інформаційні), або в `std::cerr` (помилки). Перелік типових повідомлень.

**Інформаційні:**

- `[Config] Loaded from: config.json` – конфігурацію успішно прочитано;
- `[Config] File not found, using defaults: config.json` – файл відсутній, використано значення за замовчуванням;
- `[Engine] Vulkan initialized` – стек *Vulkan*-об'єктів успішно ініціалізовано;
- `[MainMenu] UI created: 2 centered buttons (New Game, Exit)` – головне меню готове до взаємодії;
- `[UI] New Game clicked! Starting game...` – користувач почав нову гру;
- `[UI] Exit clicked! Closing game...` – користувач ініціював вихід;
- `[F3] Debug overlay: ON / OFF` – перемикання дебаг-оверлею;
- `[UIRenderer] Initialized with Pipeline2D` – *2D*-конвеєр для інтерфейсу готовий.

**Попередження та помилки:**

- `[Config] Parse error: <details>` – синтаксична помилка у файлі *JSON*; програма продовжить роботу зі значеннями за замовчуванням;
- `[Engine] Failed to create window` – не вдалося створити вікно через *GLFW* (типово – відсутність дисплейного сервера);
- `[Engine] Failed to create Vulkan instance` – у системі немає сумісного *Vulkan*-драйвера;
- `[Engine] Failed to create device` – не знайдено графічного процесора з підтримкою необхідних розширень *Vulkan*;
- `[UIRenderer] TTF font failed, falling back to bitmap font` – файл шрифту не знайдено, використовується вбудований растровий шрифт *5×7* пікселів (відображає лише цифри та латинські літери, потрібні для *FPS*-лічильника).

## 3.10 Завершення роботи

Коректне завершення роботи з програмою можна виконати декількома способами. Перший – натиснути кнопку **Exit** у головному меню; другий – натиснути стандартну системну кнопку закриття вікна; третій – у меню паузи натиснути **Main Menu** і потім **Exit**. У всіх випадках виконується однакова послідовність: головний цикл `mainLoop` виходить за умовою `m_window.shouldClose()`, далі викликається `vkDeviceWaitIdle` для синхронізації з графічним процесором, після чого деструктор класу *Engine* у зворотному порядку викликає `cleanup` для всіх підсистем – *WorldRenderer*, *FrameSync*, *Swapchain*, далі знищується *VkSurfaceKHR*, *VkDevice*, *VkInstance* і, нарешті, *GLFW*-вікно. Завдяки використанню принципу *RAII* у всіх обгортках *Vulkan*-об'єктів виключені витоки відеопам'яті.
